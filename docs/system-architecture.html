01 / OVERVIEW

本体は、ひとつのWebアプリ

ブラウザの画面とFastAPIが連携し、Python側で文書の読込・検出・マスクを行います。正解データのレビューとベンチマークは、開発用の別経路です。

02 / DETECTION

候補を作り、文書内でそろえる

analyze_document()が文書全体を受け取り、各ブロックを解析します。通常のテキスト入力も、1ブロックの文書として同じ処理を通ります。

  1. 元の本文を保ち、検出用の表記を整える

    ルール用には全角英数字やハイフン類を文字数が変わらない形で正規化します。GiNZA用には漢字の字間空白を詰める別の処理を使い、対応表で検出位置を元の本文へ戻します。原本の文字列自体は書き換えません。

  2. 複数の検出器から候補を集める

    GiNZA NER

    固有表現認識と形態素情報を利用。人名・組織・地名・一部の施設ラベルを取り込み、名簿欄や署名の氏名範囲を補完します。NLPは各ブロックにつき1回です。

    Presidio Pattern

    電話・郵便番号・メール・URLの形式を抽出。型番などの文脈やURL末尾を確認します。Presidioのパターン機能を使い、NLPモデルはGiNZA側で扱います。

    日本固有ルール

    住所・日時・法人表記・施設名・担当者欄などを補完。IPの構文、カードのLuhn検証、番号の周辺文脈も扱います。

    PII辞書

    利用者が登録した文字列と一致する範囲を候補化します。英字の大文字・小文字は区別しません。最終的な重複解決では最優先です。

  3. 確かな氏名・組織名を、同じ文書の別の箇所にも適用する

    文脈や形態素から得た、一定条件を満たす3文字以上の候補を使います。分類が曖昧な語は除外し、同じ表記を他のブロックでも探します。姓だけの一致には広げず、メール内部や語の途中への拡張を抑えます。

    この補完情報は1回の文書解析内だけで保持します。別文書への持ち越しや、PII辞書への自動登録はありません。施設を含むLOCATIONは繰り返し補完の対象外です。

  4. 分類の補正・対象分類の絞り込み・重複解決

    根拠のある文脈補完でGiNZAの範囲や分類を補正してから、有効な分類だけを残します。重なる候補は、検出元の優先度・スコア・範囲の長さ・開始位置の順で選びます。

  5. 元の文字位置を持つFindingを返す

    block_id・start・endで範囲を特定。entity_type・text・source・score・idを添えて、画面とマスク処理が同じ候補を扱えるようにします。

文字位置の約束：startを含み、endを含まないPython文字列のコードポイント単位です。位置はブロック内の元本文を基準にし、ブラウザ側もコードポイント単位で選択範囲を扱います。

候補が重なったときの優先順位

高い順に、辞書（5）、電話・メール・URL等のパターンと番号検証（4）、一部の明示的な氏名・組織文脈（3.5）、住所・日時・業務文脈・形態素補完・繰り返し（3）、GiNZA単独（2）です。同順位ではスコア、長い範囲、早い開始位置の順です。

文脈によるGiNZA候補の補正は、この順位付けの前にも行います。「長い候補を常に採用する」という仕組みではありません。実装：JapanesePiiEngine.analyze_document()と_resolve_overlaps()。

03 / REVIEW & OUTPUT

採用した範囲だけを、原本へ反映する

自動候補を解除したり、本文を選択して手動候補を追加したりできます。追加時は「選択箇所のみ／同じ文字列すべて」と、任意の辞書登録を選べます。確認済みかどうかを自動判定する仕組みはありません。

入力読込単位マスクと出力
テキスト入力欄の文字列1つ後方から選択範囲を置換。画面では分類ラベルを表示し、APIはマスク文字にも対応。TXTファイルを文書APIへアップロードする機能はない。
DOCX段落・表・ヘッダー・フッター段落内の複数runにまたがる範囲を、各runへ分配して文字を置換。DOCXとして保存。
PPTXテキスト枠・表・グループ内の図形・ノート対象テキストのrunへマスク文字を書き戻し、PPTXとして保存。
PDFフォント情報で復号した文字。同一行の複数Tj/TJ演算子を連結選択したグリフの文字データを除去し、文字の送り幅を維持して黒塗りを描画。元の表や配置を保つ。マスク文字の指定によらず黒塗り。

文書APIはDOCX・PPTX・PDFのみ、1ファイル25 MiB以下。PDFで1グリフが複数のUnicode文字を表す場合は、その一部を選択してもグリフ全体を除去します。

テキストと文書では、候補の管理場所が違う

テキストでは、画面が本文・候補・採用IDを持ち、マスク時にまとめて送ります。文書では、サーバーが原本・ブロック・候補を保存し、マスク時はセッションIDと採用IDで参照します。文書の手動候補の追加・削除もサーバーへ保存します。

自動候補はチェックを外して不採用にできます。削除APIで消せるのは手動候補だけです。文書のマスクでは、保存済み候補に存在するIDだけを採用します。

05 / RUNTIME & DATA

モデルと、利用者が保存するデータを分ける

実行時の検出・マスクには外部API、モデルの自動ダウンロード、CDNを使いません。依存パッケージとモデルは、環境構築時にインストールします。

実行環境

DockerではUvicornを1ワーカーで起動し、FastAPIが画面とAPIを配信します。ローカルPythonでも動きます。GiNZAは必要になった時点でプロセス内に読み込みます。

KOTOBA_VEIL_DISABLE_NLP=1ならルールと辞書のみ。モデルを読み込めない場合もNLPなしで動き、nlp_availableで状態を返します。

モデルと辞書の違い

ja_ginzaと形態素解析用の辞書は依存環境に含まれます。利用者のPII辞書は別のSQLiteで、画面から更新できます。PII登録では形態素解析用の辞書を再構築しません。

通常の保存基点はdata/。KOTOBA_VEIL_DATA_DIRで変更可能。Docker Composeでは専用データボリュームを利用。
保存先内容と寿命
kotoba-veil.sqlite3PII辞書の語・分類・メモ・作成日時。利用者が削除するまで保持。
sessions/{session_id}/input.*原本、session.jsonメタデータ、analysis.json本文と候補、masked.*出力。自動削除・期限切れ処理は未実装。
ブラウザのメモリ入力・候補の採用状態・表示中の結果。画面のリセットでサーバーの原本・解析結果は削除されない。
解析呼び出し内のメモリ文書内補完に使う氏名・組織名。解析が終われば次の文書には引き継がない。
「ローカル処理」とネットワークの境界

本体は入力本文を外部サービスへ送信しません。ただし、アプリ自身にログイン認証や外向き通信を遮断する機能はありません。現在のcompose.yamlの8000:8000はlocalhost限定のポート指定ではありません。実際のアクセス範囲は起動設定とホスト側のネットワーク設定で決まります。

HTTPにはCSP、Cache-Control: no-storeなどを設定しています。これらは認証や保存データの暗号化・削除を代替するものではありません。オフライン起動の確認手順はREADME.mdにあります。

指標と速度比較の読み方

完全一致は分類・開始位置・終了位置の一致。文字被覆率は分類を問わず正解文字をどれだけ覆ったか、検出文字の適合率は検出範囲のうち正解に含まれる文字の割合です。人名・住所の全範囲被覆率も別に集計します。候補を全採用した場合の評価であり、出力ファイルの安全性とは別です。

郵便番号の「〒」を余分に覆う境界差は、文字が残る見逃しと分けて報告します。暫定タグでの評価には--allow-draftの明示が必要です。

速度は、同じ端末・入力・辞書条件で前後各3回以上、実行順を交替し、別プロセスで測ります。各回10文書のウォームアップ後に、総検出時間・1文書の中央値とp95・モデル読込時間を記録。採点や保存は検出時間から除外します。

今回の合格条件は、文字被覆率95%以上、人名・住所の全範囲被覆率各95%以上、検出文字の適合率98%以上、総検出時間の中央値が修正前の2倍以内です。比較ツールは目標未達でも結果を保存し、終了コード1を返します。

PDFの読込・マスク保存を含む比較には、別のbenchmarks/compare_performance.pyを使います。再実行コマンド、スナップショットとハッシュの扱いはbenchmarks/README.mdを参照してください。

07 / LIMITS & CHECKS

対応範囲と、変更時に確かめること

PDF・画像の制約

OCRは未実装。抽出可能な文字がないPDFは案内付きでエラーになります。未対応のフォント・幅情報、Form XObject、ActualTextもエラーにします。画像や注釈など、ページ本文以外の内容はこのマスク処理の対象外です。

Office・検出の制約

SmartArt・チャート・埋込ファイル・任意XML拡張などは完全処理の対象外です。マクロ付き形式は受け付けません。検出には見逃し・誤検出が残るため、候補と出力の確認が必要です。

変更箇所に対応するテストとCI
  • 検出・文字位置・文書内補完：tests/test_detectors.py、test_roster_fields.py、test_business_detection.py
  • 読込・マスク・文字除去：tests/test_documents.py、test_pdf_documents.py
  • 画面・API・手動追加・辞書：tests/test_static_ui.py、test_api.py、test_manual_findings.py、test_database.py
  • 採点・正解レビュー・比較：tests/test_benchmarks.py、test_reannotation.py、test_generated_annotation_review.py、test_performance_comparison.py

.github/workflows/ci.ymlはテストとカバレッジ、ルール単独／GiNZA込みの合成ベンチマーク、名簿の回帰、ライセンス監査、Dockerビルドを実行します。ローカルの218文書と原本PDFはGitに含めず、共有CIの対象外です。

python -m pytest --cov
python -m benchmarks.run --output build/benchmark-report.json
python scripts/check_licenses.py

合成データのCI基準はbenchmarks/README.mdを参照。絶対的な処理時間は共有CIの合否には使わず、同じ端末での前後比較で確認します。HTMLの資料テストは内容の存在確認であり、実装との一致を自動保証するものではありません。
